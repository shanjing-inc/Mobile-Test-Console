# 重制代码审核设计

## 审核边界

本次审核以 `TestTask.retryOf` 和页面选择参数为两个入口，沿完整数据流检查共享契约、服务端、Runner、项目 Provider、Result Bundle、Web 投影与清理行为。Trellis 任务文件、规范和开发日志作为同一工作成果的一部分，在提交前按内容关联性核对。

## 数据流

```text
页面目录与用户勾选
  -> POST /api/tasks
  -> 冻结页面 ID 参数
  -> TaskManager / RunPlan
  -> Runner 命令与项目 Provider
  -> Result Bundle

来源结果中的复测操作
  -> POST /api/tasks/:taskId/retry
  -> TaskRetrySource
  -> Runner metadata / 模板变量 / 环境变量
  -> 定向执行与结果采集
  -> 来源结果累计合并
  -> 来源行状态投影与重试链清理
```

## 核心约束

- `retryOf.taskId` 表示直接来源，遍历后代得到完整重试链。
- 复测用例通过 `caseRunId` 优先匹配，并以 `caseId`、`targetPage` 作为兼容匹配键。
- 只有通过的复测结果替换来源项；失败、取消、中断、解析失败和缺失结果保留来源项。
- 结果合并顺序由任务创建时间确定，保证兄弟与多层复测可累计先前成功结果。
- 页面范围在任务创建时展开为显式页面 ID，后续目录变化不会改变已创建任务。
- 前端禁用态提供即时约束，服务端状态校验提供最终约束。

## 审核策略

1. 静态检查所有契约生产者与消费者，确认字段命名、默认值、序列化和错误语义一致。
2. 以边界场景审阅测试有效性，确认测试在删除对应生产逻辑后能够失败。
3. 先运行针对性测试定位问题，再运行完整质量门禁验证集成行为。
4. 对确认的问题做最小范围修复，保持现有架构和兼容字段。
5. 提交前检查工作区、暂存区和最终 diff，使用中文提交信息。

## 兼容性与回滚

- `retryOf` 与 Runner metadata 均为可选字段，旧任务状态继续加载。
- `all-pages` 作为兼容输入解析，新任务保存显式页面列表。
- 修复保持现有 HTTP 路径和 Result Bundle 版本。
- 回滚点以单个问题的代码与回归测试为单位；提交前保留用户现有工作区内容。
