# 新项目接入引导设计

## 目标体验

项目卡片的接入区域变成以任务驱动的向导：用户先看到“下一步做什么、为什么要做、完成后得到什么”，再决定是否查看配置和检查细节。完成运行前条件后，界面把下一步聚焦到运行第一条测试。

## 页面边界

- `ProjectCatalogWorkspace` 保持项目登记、校验、初始化预览与应用的职责。
- `ProjectCatalogCard` 负责将现有 onboarding 状态投影为面向新手的步骤与当前任务。
- 服务端继续产出 `ProjectOnboardingStep`、工具检查、能力检查和 setup plan；本次不修改配置协议和执行契约。
- Web API 继续使用现有验证、初始化、接入设置预览和应用接口。

## 交互模型

1. 顶部展示进度、当前目标和单一主操作。优先选择第一个未验证的运行前步骤。
2. 步骤列表使用用户任务命名：准备项目配置、检查运行环境、接入可选增强能力。每项说明完成后可获得的能力。
3. 未完成步骤显示简短的行动卡：说明需要准备的内容、文件位置或命令、主按钮及“完成后自动验证”的预期。
4. health check 的命令、标准输出、失败输出和 Provider 等术语落在“查看检查详情”层，帮助文本附带通俗解释。
5. 完成运行前检查后，将主操作切换为“运行首个测试”；测试入口为空时，提示用户通过配置初始化补齐。
6. Lynx App 与小程序共用步骤外观和状态系统，通过 `integrationType` 提供对应的环境、模板和文档描述。

## 写入与复检

生成配置或能力骨架继续调用已有 preview/apply 流程。确认弹窗展示所有文件与命令，应用后复用现有自动校验并刷新 UI。该流程维持现有写入边界和失败反馈。

## 测试策略

- 扩展 Web 项目目录测试，断言当前任务、行动按钮、用户化术语、技术详情折叠区和首测入口文本。
- 保留小程序运行目标和 Lynx App 项目卡片的测试夹具，覆盖项目类型差异。
- 运行 TypeScript、lint、现有 Web 与项目目录测试。

## 回滚

本次改动局限于 Web 展示、文案和测试。回滚相应组件与样式即可恢复现有引导界面，服务端状态和项目配置保持兼容。
